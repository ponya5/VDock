Feature Research — Next Features, Audio Awareness, MCP, and Competitor Comparison

Compiled 2026-09-29 from a codebase audit + competitor feature survey (Elgato Stream Deck, Virtual Stream Deck, Touch Portal, Macro Deck, MATRIC).

What VDock already has (so gaps are real, not assumed)

  • Grid decks with scenes, pages, folders-as-scenes, configurable rows/cols, button merge/split, per-scene backgrounds, animated backgrounds.
  • Control types: push buttons, sliders (volume / app-volume / brightness / ui-brightness), toggles (toggle_action), keyboard/wheel input, quick-jump preset chips.
  • Macro + multi-action: sequential steps only (macro_action: hotkey/delay/text/click/clipboard; multi_action: action list + stop-on-error). No conditionals, loops, or variables.
  • State-aware buttons: buttonState store (badges/icons), agent-state-aware actions (ready/working/permission glow), performance-metric buttons.
  • Backend monitors pushed over Socket.IO: volume_monitor (system_volume events), app-monitor (foreground app), agent session state, job runner.
  • Media actions: keypress-only (nircmd sendkeypress media_*) — no now-playing metadata, no play state feedback.
  • Per-app volume (Windows session audio via pycaw GetAllSessions()).
  • Screensaver: clock/weather/news/markets/sports/world-clock widgets in a drag/resize layout editor, with an honest "unavailable" state.
  • Browser client: the whole deck is a web app — any LAN device with a browser is already a control surface (QR connect, mobile chrome, mobile agent console).
  • /api/actions/execute HTTP endpoint — already an inbound webhook surface (anything on the network can trigger any deck action).
  • Plugin system (BasePlugin + plugin_manager, OBS example) and IDE/agent packs with hook-installed state reporting.

2. "Winamp" spectrum screensaver + Spotify recognition

Two separate capabilities — both feasible, different costs.

2a. "What's playing" — yes, VDock can recognize Spotify

Windows exposes SMTC (GlobalSystemMediaTransportControlsSessionManager), readable in Python via the winsdk package (winsdk.windows.media.control). It reports:

  • Track title, artist, album, album art thumbnail
  • Play/pause state, position/timeline
  • Source app ID (spotify.exe, chrome.exe, msedge.exe, VLC, …)

Anything modern registers with SMTC — Spotify, browsers, most players.

Platform notes:

  • macOS — osascript can query Spotify/Music directly, or nowplaying-cli covers the system Now-Playing surface.
  • Linux — MPRIS over DBus (playerctl).

Bonus: pycaw's GetAllSessions() (already used by the app_volume slider) can tell which process is currently outputting audio even without SMTC — "spotify.exe is making sound" is detectable today for free.

Design shape: a services/now_playing.py monitor mirroring volume_monitor's emitter/spawner pattern — poll SMTC ~1.5 s, emit now_playing {title, artist, album, art_url, playing, source_app} on change. Consumers: a Now-Playing screensaver widget, media buttons that show real play/pause state, and per-app volume highlighting the active session.

2b. Spectrum visualization

Real path: WASAPI loopback capture (record what the default render device is playing) → FFT → frequency bins → Socket.IO → canvas bars in a new screensaver widget.

  • Capture: pyaudiowpatch or soundcard (both do WASAPI loopback on Windows); numpy FFT → ~24 bands; emit audio_spectrum {bands, playing} at ~15–20 fps — trivial CPU.
  • Frontend: canvas widget inside ScreenSaver.vue's existing widget/layout system (drag/resize/editor all generic already).
  • Keep the capture on its own thread, not inside the COM audio worker — loopback manages its own COM objects.

Honest limits:

  • Loopback capture is Windows-only in practice. macOS needs a virtual driver (BlackHole) — no system-audio tap otherwise. Linux can capture the PulseAudio/PipeWire monitor source.
  • Cheap fallback (every platform, zero new deps): IAudioMeterInformation peak level via the existing audio worker → a single bouncing VU meter, not a spectrum.

Suggested order: SMTC now-playing first (higher value, lower risk — pure reads), spectrum as phase 2 reusing the same monitor plumbing.

3. MCP — what it would give VDock

Two directions; one is clearly better.

VDock as an MCP server (the good one)

Expose deck capabilities as tools: press_button, switch_scene, show_notification, get/set_volume, deck_screenshot. Your agent integrations (Claude Code, Cursor, Antigravity hooks) then become bidirectional: today VDock watches agents; with MCP an agent can act on the panel — "when the build finishes, flash the Alerts scene," "push a badge when I need permission." The panel becomes a physical output device for agents — genuinely differentiated (Stream Deck doesn't do this).

Effort caveat: MCP stdio wants to spawn a server per client — awkward because the backend is already running. The right shape is HTTP/SSE (Streamable HTTP) transport exposed from Flask (or a side port). Moderate work; real payoff if you use agents heavily.

VDock as an MCP client (buttons call MCP tools)

Plausible but weaker — http_request/run_command actions already cover most of what an MCP tool call does, minus schema discovery.

The copycat shortlist, ranked for this product

  1. Headless triggers / schedules — you already have every piece except the trigger: app-monitor events, agent hooks, and the execute-API webhook. Add a triggers table (app-opened → scene, time → action, webhook → macro) and VDock gains Touch Portal's "event-driven" tier cheaply.
  2. Conditional button styles — the state plumbing exists; a per-button "if system_volume.muted → red icon" rule layer generalizes agent/metric states to everything.
  3. Macro variables + branches — if/else, wait-until, and {{variable}} substitution in macro_action steps; keep the editor simple (structured rows, not a scripting language).
  4. Embedded widgets on the grid — an embed_url button face renders a sandboxed iframe (clock, Grafana panel, camera feed). One face component + a CSP exception.
  5. Global-hotkey summon (desktop app) — Electron globalShortcut → show the window at cursor / center on demand. Only meaningful when the packaged app is the target.
  6. Sensor/trackpad mode — turn a phone surface into a trackpad/media remote. Fun, but lowest value on a fixed 7" panel.

Prioritized roadmap (recommendation)

  1. SMTC now-playing (§2a) — awareness is the theme across every gap.
  2. Notification-to-panel for agent-waiting state — the panel flags which agent needs you.
  3. Spectrum screensaver (§2b) — the Winamp moment.
  4. Triggers/schedules (§4.1) — unlocks headless automation cheaply.
  5. MCP server (§3) — makes agents bidirectional.
  6. Timer buttons, system-stats widget — quick wins to slot anywhere.
Items 1+2 compound: a panel that knows what's playing and which agent is waiting is the product this hardware wants to be.
